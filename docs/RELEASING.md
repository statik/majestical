# Releasing

A release is one click: run the **Release** workflow from main (Actions →
Release → Run workflow, or `gh workflow run release.yml`). Nothing in the
flow needs a version-bump commit:

- The **version** is computed from conventional commits since the last tag —
  `fix:` → patch, `feat:` → minor, a `!` breaking marker → major, clamped to
  the 0.x range by `scripts/clamp-version.sh` until 1.0.0 ships
  deliberately. The workflow's `version` input overrides the computation;
  with no releasable commits and no input, the run stops instead of
  releasing nothing new.
- The **notes** are the rolling draft that
  `.github/workflows/release-drafter.yml` maintains as PRs merge (see
  [Release notes and labels](#release-notes-and-labels)).
- The **binaries** carry the computed version because
  `scripts/version-stamp.sh` writes it into the five version locations in
  the build tree before building. The stamp is never committed: the
  versions in the repository stay frozen, and git tags are the source of
  truth for what was released. `scripts/version-sync.sh` still guards that
  the five locations agree with each other — in CI against drift, and at
  the end of every stamp against a stamp that missed a file.
- The **git tag** is created when the release is published, pointing at the
  main commit the draft was pinned to when the run started. Pushing a tag
  by hand no longer triggers anything.

Publishing is the run's last job. Nothing reaches users until it runs: with
the `publish` input on (the default), the run ends published and installed
apps see the update; with it off, the draft waits for
`gh release edit vX.Y.Z --draft=false` or deletion.

The release receives:

- `Majestical.app.tar.gz` and a `.dmg` for `aarch64-apple-darwin`, built by
  `tauri-action`
- `latest.json`, the updater manifest, and a `.sig` beside each bundle (see
  [Updater keys](#updater-keys))
- `maj-<tag>-aarch64-apple-darwin.tar.gz` and `checksums.txt`, the
  command-line catalog. `checksums.txt` covers only that tarball: the desktop
  bundles carry a `.sig` each, which the updater verifies against the
  compiled-in public key, so a SHA line beside them would be the weaker of
  the two checks.
- `licenses.html`, the third-party crate licenses, generated by `cargo-about`
  from `about.toml` and `about.hbs`

The bundle's `minimumSystemVersion` is 10.15 and cannot go lower:
`tauri build` exports it as `MACOSX_DEPLOYMENT_TARGET`, and whisper-rs-sys's
vendored whisper.cpp uses `std::filesystem` (introduced in macOS 10.15), so
a lower floor fails the desktop jobs at compile time. Only the release
pipeline runs the bundler, which is why no CI job catches this — the
v0.1.0-rc1 dry run did.

Apple silicon only. Windows and Linux artifacts, code signing, and
notarization are not in this phase.

### No Intel build

`ort-sys` 2.0.0-rc.13 publishes no prebuilt ONNX Runtime for
`x86_64-apple-darwin` — its distribution table lists `aarch64-apple-darwin`
as the only macOS target — so an Intel build stops in the build script:

```text
no prebuilt binaries available for target x86_64-apple-darwin
```

That is a compile-time stop in `crates/index`, well before anything is
bundled, and it has been true since phase 5 put `ort` in the tree. The old
release workflow predated that, so the spec's Intel commitment had been
quietly unbuildable ever since; the `v0.1.0-rc2` dry run is what surfaced it.
**Decision, 2026-08-05: ship Apple silicon only.** Revisit if `ort` restores
`x86_64-apple-darwin` prebuilts, or if the semantic stack becomes optional at
build time so an Intel binary can be built without it. Building ONNX Runtime
from source in CI, or vendoring one via `ORT_LIB_LOCATION`, are the other two
routes; both are recorded in the watchlist and neither is worth its cost for
a machine class Apple stopped selling.

## Cutting a release

```bash
gh workflow run release.yml
# `gh run watch` with no argument prompts for a run; name the release run.
sleep 5 && gh run watch "$(gh run list --workflow=release.yml --limit 1 \
  --json databaseId --jq '.[0].databaseId')"
```

A Tauri release build is slow; the desktop job plus the CLI job take a
while. When the run finishes, the release is published and the tag exists —
check the desktop job's log for the key-mismatch warning described under
[Updater keys](#updater-keys).

The draft is single by construction: the `draft` job stamps the rolling
draft (creating it only if none exists) before any build starts, and
`tauri-action` is handed its id, so no build job ever creates a release.
Restoring a second build target cannot split the draft.

To exercise the pipeline without shipping, give the run an `-rc` version and
keep the result a draft:

```bash
gh workflow run release.yml -f version=0.2.0-rc1 -f publish=false
```

The draft is marked prerelease and its bundles carry the rc version. To
abandon it — or any unpublished draft — delete it; no tag exists until a
release is published, so there is nothing else to clean up:

```bash
gh release delete v0.2.0-rc1 --yes
```

The next merge to main recreates the rolling draft with the same accumulated
changelog, so deleting a draft never loses notes.

## Release notes and labels

release-drafter files each PR under a heading by parsing its
conventional-commit title — `feat:` → Features, `fix:` → Fixes, `docs:` →
Documentation, `chore:`/`refactor:`/`test:`/`ci:`/`build:`/`perf:`/`style:`
→ Internal, anything unparseable → Other. The release workflow computes the
next version from the same titles, which is why
`.github/workflows/pr-title.yml` rejects PRs whose titles do not parse:
squash-merge makes the title the commit message, and a mistyped `feat:` is
a release that never happens. Three labels carry meaning: `dependencies`
(applied by Dependabot itself) files a PR under Dependencies,
`skip-changelog` keeps a PR out of the notes entirely, and `major` forces a
major version suggestion in the rolling draft's name.

Between releases the rolling draft's name shows release-drafter's own
next-version estimate. It is cosmetic — the version that ships is the one
the release workflow computes at dispatch time.

To adjust wording, edit the draft in the GitHub UI any time before
publishing; no commit is involved. The boilerplate above the changelog
(system requirements, Gatekeeper note) lives in the `template` key of
`.github/release-drafter.yml`; editing it is an ordinary PR, not a
release-day change.

## Updater keys

The app checks for updates on startup and offers a banner when one exists
(`apps/desktop/src/lib/updater.ts`). Updates are signed: Tauri verifies every
downloaded bundle against the public key compiled into the app, so the private
key is what makes shipping an update possible at all.

The public half lives in the repository, in
`apps/desktop/src-tauri/tauri.conf.json` under `plugins.updater.pubkey`, with
key ID `9D3AD6D3C4DA4E46`. Three things make the updater work, and they are
already in place:

1. `plugins.updater` in `tauri.conf.json` — the public key and the endpoint
   the app polls.
2. `bundle.createUpdaterArtifacts: true` in the same file. Without it the
   bundler produces no `.tar.gz`/`.sig` pair for the updater to download, and
   `latest.json` ships listing no platforms.
3. `.plugin(tauri_plugin_updater::Builder::new().build())` in
   `apps/desktop/src-tauri/src/lib.rs`. This line and the config in step 1
   must stay together — the updater's config has no default for `pubkey`, so
   a registered plugin with no `plugins.updater` block fails to deserialize
   its configuration and the app exits on startup instead of opening a
   window.

### The private key

The private half lives in two secrets scoped to the `release` GitHub
Environment, `TAURI_SIGNING_PRIVATE_KEY` and
`TAURI_SIGNING_PRIVATE_KEY_PASSWORD`. The `desktop` job in `release.yml`
declares `environment: release`, so `secrets.TAURI_SIGNING_PRIVATE_KEY` and
its password resolve from the environment there; GitHub falls back to a
repository secret of the same name if the environment has none, so moving
the values did not require a workflow change beyond adding that
`environment:` line. `release.yml` passes them to `tauri-action`.

Create the environment once with:

```bash
gh api -X PUT repos/statik/majestical/environments/release
```

then move the secret values into it with:

```bash
gh secret set TAURI_SIGNING_PRIVATE_KEY --env release
gh secret set TAURI_SIGNING_PRIVATE_KEY_PASSWORD --env release
```

The old repository-level secrets stay in place until a release dry run
proves the environment-scoped ones work end to end; only then should they be
deleted (`gh secret delete TAURI_SIGNING_PRIVATE_KEY`, and likewise for the
password).

**Nothing has yet proved that those secrets hold the private half of the
public key above**, and the artifacts cannot tell you. `tauri-cli` signs with
whatever private key it is handed and merely logs a warning when that key
does not match the configured `pubkey` (`crates/tauri-cli/src/bundle.rs`, the
`signature.keynum() != public_key.keynum()` branch). A build with the *wrong*
key still produces a `.sig` beside every bundle and a `latest.json` listing
both platforms — every artifact-level check passes, and installed apps then
reject the update.

So check the log, not the assets. In the desktop job's `tauri-action` step:

```text
The updater secret key from `TAURI_SIGNING_PRIVATE_KEY` does not match the
public key from `plugins > updater > pubkey`.
```

That line must **not** appear. Searching the run for `does not match the
public key` is the whole check:

```bash
gh run view --log --job <desktop-job-id> | grep -i "does not match the public key"
```

Silence there means the keys pair. The definitive proof is one step further
out and cannot be had from CI at all: an already-installed app taking a real
update from a published release. Until that has happened once, treat the
pairing as probable rather than certain.

Missing secrets do not degrade gracefully any more — that changed when the
updater was armed. With a `pubkey` configured and `createUpdaterArtifacts`
on, `tauri-cli` treats the private key as required and the desktop job fails
at the bundling step: `A public key has been found, but no private key` when
the variable is absent, or `failed to decode secret key` when it is present
but empty, which is what a missing GitHub secret produces. The result is no
release with desktop bundles in it. That is the better failure — a loud stop
beats silently shipping unsigned artifacts that no installed app can ever
verify.

To regenerate the keypair from scratch:

```bash
cd apps/desktop && pnpm tauri signer generate -w /tmp/majestical-updater.key
gh secret set TAURI_SIGNING_PRIVATE_KEY --env release < /tmp/majestical-updater.key
gh secret set TAURI_SIGNING_PRIVATE_KEY_PASSWORD --env release  # the password chosen above
trash /tmp/majestical-updater.key
```

A new keypair means replacing `plugins.updater.pubkey` in the same commit.
Losing the private key means no existing installation can ever be updated
again; a new key only reaches users who reinstall by hand.
