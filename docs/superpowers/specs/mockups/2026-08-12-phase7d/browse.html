Browse — two layout candidates

Both mockups use the app's real visual language (Layout C shell, existing tokens and card grid). Browse navigates cataloged assets only, works identically for offline drives, and any folder shows its entire subtree flattened into one grid — the Kyno drilldown. The sidebar change shown here is shared by every variant: Browse, Ingest, and Organize join Search and Volumes, in workflow order (find → browse → bring in → file away → hardware).

Variant A — folder tree pane

A persistent tree keeps you oriented across volumes; the grid always shows the selected node's subtree.

  • 1Child folders as a pill row with item counts — the drill-down affordance. The root level shows one pill per volume.
  • 2No fourth column: the grid keeps Search's width, and the surface reuses Search's exact grid/inspector machinery — least new layout code of the two.

My read: A is the stronger Browse for a media catalog — folder trees are the mental model every DIT already has, offline volumes stay visible in the tree instead of being something you have to remember to drill into, and the orientation cost of B's pill-row (where am I? what's beside me?) grows with catalog depth. The fourth column is real but tolerable: the tree can collapse to a strip once a selection is made.

Both variants share: flatten-on-by-default, degradation notices verbatim under the count line, the existing inspector unchanged, and hover-scrub as drawn in A's note 5.
